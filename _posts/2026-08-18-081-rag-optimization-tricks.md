本文整理 RAG 检索链路上常用的优化技巧：从召回阶段的**滑动窗口**、**BM25 结构化**、**中文分词**，到融合阶段的 **Rank Fusion / Score-aware RRF**，再到系统级的**参数消融实验**与 **Agentic 多轮检索**。每条技巧都给出动机、核心思想以及在企业知识库场景下的弊端与边界。

---

## 一、滑动窗口

检索命中一个 chunk 以后，不只返回这个 chunk，而是把它附近的 chunk 一起返回。

通过邻居参数 `r`，控制向前、向后扩展 `r` 个 chunk。

如果 `r=3`，例如，检索命中了 `[chunk3]`，最终返回：

```
Chunk0
Chunk1
Chunk2
Chunk3  ← 检索命中
Chunk4
Chunk5
Chunk6
```

也就是 `Hit Chunk ± r 邻居`。

### 直觉

因为企业知识库文档通常具有连续结构：例如：

```
第5章 设备维护规范

Chunk20:
设备维护周期为30天

Chunk21:
维护步骤包括：

Chunk22:
1. 检查电源
2. 检查传感器

Chunk23:
异常情况处理方式
```

如果只召回 Chunk22：LLM 不知道：这是哪个章节？前面的维护周期是什么？后面的异常处理是什么？

**窗口扩展后，上下文完整性提升。**

```
Chunk19
Chunk20
Chunk21
Chunk22
Chunk23
Chunk24
```

### 评估指标介绍

**Window Hit@10**：滑动窗口后的 Top 10 是否包含正确答案所在的位置，是个二元参数，只看 有还是 没有。

**Hit@10**：Top 10 检索结果里面，是否包含正确答案所在的位置，是个二元参数，只看 有还是 没有。

**Recall@10**：Top 10 检索结果中，找到了多少相关内容。Recall@10 = 3/5 = 60%

## 二、BM25 优化

### 局限

传统 BM25 只看正文，没有搜到完整关键词，则系统认为`不相关`。

### 优化思想

不要把文档看成一大段文字，而要利用文档结构信息。

企业文档通常有：标题、章节、小标题、正文、表格、摘要。

所以把："**标题 + 章节 + 正文**"拼接成一个新的检索字段。即把标题路径 + 正文进行向量化。

## 三、中文分词优化

### 局限

中文不像英文天然有空格。

例如"医疗设备维护规范"，可能会被拆分为"医疗 设备 维护 规范"，也可能是"医疗设备 设备维护 维护规范"。

### 核心思想

让搜索系统按照业务场景理解中文词。尽可能多地产生更多词。使用 jieba search 模式。

例如：

输入：

```
医疗设备维护
```

可能产生：

```
医疗
设备
医疗设备
维护
设备维护
```

## 四、混合检索后排序融合（Rank Fusion）

### 局限

混合检索通常是 BM25 + Embedding，量纲差异大，BM25 的范围是 0 ~ 无穷，Embedding 是 0 ~ 1。

### 核心思想

量纲差异导致不同路径得到的结果不能直接融合，因此直接看排名。

---

## 五、分数敏感型 RRF（Score-aware RRF）

### 局限

**RRF** 是最常用 Rank Fusion 算法。

RRF 只看排名，不看分数。

### 核心思想

在 RRF 的基础上，加入 score 即可得到 Score-aware RRF。

例如：Dense score + BM25 score + rank 的综合排序

利用更多信息：

- 排名
- 原始相关度

### 弊端

额外 score 信息：没有带来增益。

甚至可能：某一路 score 尺度偏差导致排序污染。

### 核心思想

对 chunk size、overlap、rank 数量、keyword 权重等进行系统性的多组对照实验，找到最佳的 RAG 参数组合。

## 七、Agentic RAG 多轮检索（Agentic Multi-turn Retrieval）

### 局限

传统 RAG 通常采用**单轮检索模式**：

用户提出问题后，系统进行一次检索，将 Top-K 相关 Chunk 直接交给 LLM 生成答案。

这种方式存在局限：

- 一次检索结果可能无法覆盖复杂问题所需的全部信息；
- 当首次召回结果不足时，系统无法主动发现信息缺失；
- 对于需要跨文档、多跳推理的问题，单轮检索能力有限。

### 核心思想

Agentic RAG 多轮检索是在传统 RAG 基础上引入 Agent 决策机制。

由 LLM 作为检索控制器，根据当前检索结果判断：

> 当前上下文是否已经足够回答用户问题，如果不足，则继续发起下一轮检索。

**通过最多多轮检索，提高复杂问题的信息覆盖能力。流程：**

```
第一次检索：
用户Query
    ↓
Retriever
    ↓
召回相关Chunk
    ↓
LLM判断信息是否充分
```

如果 LLM 判断当前召回的信息不足，则根据检索缺口重新生成 query 或更换检索策略、新增其他检索方案：

```
生成补充Query
    ↓
再次检索
    ↓
融合新的上下文
    ↓
生成答案
```

例如：

用户："某药物的适应症、推荐剂量以及禁忌症有哪些？"

第一次检索：找到：

```
适应症相关文档
```

Agent 判断：缺少：

```
剂量
禁忌症
```

于是生成补充检索：

```
药物名称 + 剂量 + 禁忌症
```

继续检索，补充上下文。

### 弊端

在企业知识库事实问答场景中，多轮检索可能产生负收益：

- 对于已经通过第一次检索获得完整答案的问题，额外检索会引入无关信息；
- Agent 生成的补充 Query 可能偏离用户真实意图；
- 多轮检索增加系统延迟和调用成本。

实验结果：

```
281条测试样本中：
仅解决4条低召回问题；
导致9条问题性能下降；
Hit@10下降1.8pp。   pp是百分点的意思
```

原因：大部分问题第一次检索已经能够覆盖答案，继续检索反而增加噪声。
