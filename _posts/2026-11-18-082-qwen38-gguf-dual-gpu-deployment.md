# 部署记录

本文记录 Qwen3.8-27B 的 Q6_K 量化版（6 位为主的混合精度量化，原生 256k 上下文）在两张 24 GB 显卡上的部署过程，并启用模型内置的 **MTP**（Multi-Token Prediction，多 token 预测）投机解码。

部署按实际推进顺序展开：模型资产清点与校验、运行时选型、上下文从小到大的验证、投机解码启用。各步骤记录判断依据，而非操作日志。

## 目标与核心矛盾

部署目标是在两张 24 GB 显卡上以完整 256k 上下文运行该 27B 级模型，同时启用内置 MTP 投机解码以提升吞吐。

主要约束来自显存。模型文件 24.03 GB，两张卡合计 48 GB，理论余量充足；但 256k 上下文对应的 **KV 缓存**（Key/Value Cache）按 f16 计算需 16 GiB，叠加视觉投影器、CUDA 上下文及运行时开销后，可用空间迅速耗尽。因此本次部署的核心问题是如何压缩 KV 缓存占用。

模型架构提供了可行基础。该模型为 qwen35 架构，65 层中仅 16 层使用完整注意力，其余层采用状态空间模型（**SSM**，State Space Model）。注意力层占比较低，KV 缓存规模相应减小，使其能够在 24 GB 权重之外支撑 256k 上下文。剩余缺口通过 KV 量化解决。

## 模型资产与完整性校验

主模型为单文件 **GGUF**（GPT-Generated Unified Format），大小 24,033,703,456 字节，量化类型 Q6_K。嵌入维度 5120，注意力为 4 个 KV 头，key 与 value 长度均为 256。分词器采用 GPT-2 风格 **BPE**（Byte Pair Encoding），词表 248,320。聊天模板 8,953 字节，内嵌于模型文件，无需外部模板。默认采样参数同样内嵌：temperature 1.0、top_k 20、top_p 0.95。

模型包含一层 MTP 结构，对应权重单独保留为 Q8_0 精度，是后续投机解码加速的来源。该能力在部署初期仅作记录，未启用。

文件结构核验结果：866 个张量数据区连续排列，无空洞、无重叠，末尾与文件长度一致，排除截断或拼接。另有视觉投影器 `mmproj-F16.gguf`，927,606,976 字节，用于图像与视频输入。纯文本推理可省略该文件，节省约 0.9 GB 显存；本次保留以支持视觉能力。

完整性校验采用 SHA256。哈希取自 HuggingFace 的 LFS 元数据（经镜像站访问），与本地实算值逐位一致，确认文件与上游一致，不存在截断、位翻转或补丁残留。

```bash
sha256sum \
  Qwen3.8-27B-TurboFCFusion-735-882-Here-Uncen-NEO-CODER-MAX-MTP-Q6_K.gguf \
  mmproj-F16.gguf
```

SHA256 是唯一可用于上游对账的校验方式；MD5 无上游基准，仅可作为本地基线用于后续复查。使用自带校验的下载工具时，该校验由客户端完成。

## 运行时选型

运行时选型首先评估 vLLM，结论为不可用。模型仓库仅提供 GGUF，无 bf16 或 safetensors 权重；vLLM 对 GGUF 的支持仍属实验性质，仅覆盖少量主流架构，本模型的两项特征均超出支持范围：混合状态空间架构未列入支持列表，MTP 附加结构无法识别。

其次评估环境中已部署的 Ollama。其程序内未包含该架构标识，版本过旧，导入 GGUF 会在加载阶段失败；升级受网络条件限制，发布包所在链路不可用。

排除上述两项后采用 llama.cpp。其 CUDA 镜像原生支持该架构与 MTP，镜像标签为 `server-cuda`。版本选择未采用最新版，而是先部署可用版本 b12464，镜像大小 4.38 GB。

镜像导入后核对版本差异：该版本落后上游 34 个提交。逐项检查后，与本模型相关的仅有一项权重缩放修复，该修复在当前架构实现中已包含，其余提交与本模型无关。该核对排除了版本因素导致输出异常的可能。

镜像拉取在本地链路反复失败，报 `unexpected EOF`。经排查，镜像仓库至本地链路 RTT 约 195 ms，拥塞窗口为 10，2 GB 级镜像层传输中断。最终改为离线导入：在外网环境保存镜像，传输后于本地加载。

```bash
# 外网机器
docker pull ghcr.io/ggml-org/llama.cpp:server-cuda
docker save ghcr.io/ggml-org/llama.cpp:server-cuda -o llama.tar

# 传到本地后
docker load -i llama.tar
```

导入完成后镜像归档文件已无用途，删除可释放约 2.5 GB 空间。

## 启动命令与参数释义

镜像导入后未直接启用 256k 上下文，而是先以 32768 启动最小可用配置，用于验证推理链路、聊天模板与显存占用，将显存不足与参数错误两类问题分离。健康接口与模型列表均正常后，再放大上下文。

上下文提升至 262144 时出现显存不足。原因是 256k 上下文的 f16 KV 缓存约需 16 GiB，超出两张 24 GB 卡的可用余量。解决方式为启用 KV 缓存量化，将其压缩至约 8 GiB。该配置存在依赖关系：KV 量化要求 **Flash Attention**（分块计算注意力的实现）同时启用，两者需一并配置。

上下文稳定后启用投机解码，启动参数加入 MTP 草稿。该模型仅有一层 MTP，草稿链较短，实测平均命中长度 2.18 至 2.54，因此草拟数量设为 2，依据实测值而非经验值。同时观察到两卡层分布不均：第二张卡占用 18.9 GB，第三张卡占用 22.1 GB。理论上可重新分配以均衡负载，但当时显存处于安全范围，未作调整。

最终启动命令：

```bash
docker run -d --name llama-qwen38 \
  --gpus '"device=2,3"' \
  -v /models/models:/models:ro \
  -p <HOST_PORT>:8080 \
  --restart unless-stopped \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /models/Qwen3.8-27B-TurboFCFusion-Q6/Qwen3.8-27B-TurboFCFusion-735-882-Here-Uncen-NEO-CODER-MAX-MTP-Q6_K.gguf \
  --mmproj /models/Qwen3.8-27B-TurboFCFusion-Q6/mmproj-F16.gguf \
  -ngl 99 --tensor-split 1,1 \
  -c 262144 -ctk q8_0 -ctv q8_0 -fa on --jinja \
  --spec-type draft-mtp --spec-draft-n-max 2 \
  --host 0.0.0.0 --port 8080
```

参数说明：

| 参数                 | 配置值                      | 释义与理由                                                |
| -------------------- | --------------------------- | --------------------------------------------------------- |
| `--gpus`             | `device=2,3`                | 指定容器可见的显卡，仅使用两张空闲卡                      |
| `-v`                 | `/models/models:/models:ro` | 以只读方式挂载模型目录，避免容器写入损坏文件              |
| `-p`                 | `<HOST_PORT>:8080`          | 宿主机端口映射至容器内监听端口                            |
| `--restart`          | `unless-stopped`            | 异常退出后自动恢复，手动停止后不重启                      |
| `-m`                 | 主 GGUF 路径                | 指定容器内主模型文件                                      |
| `--mmproj`           | 视觉投影器路径              | 加载多模态投影器以支持图像输入；纯文本场景可省略          |
| `-ngl`               | `99`                        | 加载至显存的层数，99 表示全部 65 层                       |
| `--tensor-split`     | `1,1`                       | 两张卡按 1:1 分配权重层                                   |

## 压测结果

部署完成后进行单请求压测，四个槽位均空闲。短上下文（68 token 提示词）下 decode 稳定在 50 至 53 tok/s，生成 200 token 约 3.8 至 4.3 秒。中等上下文（3,668 token）时 prefill 达到 1,475 tok/s，decode 为 53.6 tok/s，端到端 3.8 秒。长上下文（124,869 token）prefill 降至 916.8 tok/s，耗时 106.9 秒，decode 33.3 tok/s，端到端 110 秒。满上下文（257,469 token，接近 256k 上限）prefill 进一步降至 496.8 tok/s，耗时 268 秒，decode 23.2 tok/s，端到端 273 秒。

| 场景       | 输入 token | Prefill     | Decode        | 端到端                   |
| ---------- | ---------- | ----------- | ------------- | ------------------------ |
| 短上下文   | 68         | —           | 50 ~ 53 tok/s | 200 token 约 3.8 ~ 4.3 s |
| 中等上下文 | 3,668      | 1,475 tok/s | 53.6 tok/s    | 3.8 s                    |
| 长上下文   | 124,869    | 916.8 tok/s | 33.3 tok/s    | 110 s（prefill 106.9 s） |
| 满上下文   | 257,469    | 496.8 tok/s | 23.2 tok/s    | 273 s（prefill 268 s）   |

规律明确：上下文增长时 prefill 与 decode 同步下降，原因在于注意力计算量与 KV 读取量随序列长度增加。满上下文可完成且容器存活、显存无溢出，说明 256k 配置在资源上成立；但端到端 273 秒仅适用于离线处理长文档，交互式场景应将上下文控制在 32k 以内。

并发测试：服务配置 4 个槽位，共享统一 KV 池。四路并发时单请求 decode 降至 10 至 36 tok/s，总吞吐约为单路的 2 至 3 倍。瓶颈位于 GPU 算力而非调度；同时，高并发下各请求可用上下文会相互挤压。

## 接口验证

服务提供 OpenAI 兼容接口，支持流式与非流式。非流式请求体需提供 `model`、`messages`、`temperature`、`max_tokens`。

验证中有两项需注意。响应同时包含 `reasoning_content` 与 `content`：前者为思维链，后者为正式回答，两者均计入 `completion_tokens`。流式调用需设置 `stream: true`，并使用可关闭缓冲的客户端（如 curl 的 `-N`）。响应为标准 **SSE**（Server-Sent Events），依次推送 `reasoning_content` 增量、`content` 增量，最后以 `data: [DONE]` 结束。

```bash
curl -N http://127.0.0.1:<HOST_PORT>/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-27b",
    "messages": [{"role": "user", "content": "写一个快速排序"}],
    "temperature": 0.7,
    "max_tokens": 1500,
    "stream": true
  }'
```

参数边界：上下文总预算 262,144 token，单次输出上限为 256k 减去输入长度；服务端默认不限制生成长度，过大的 `max_tokens` 不会报错，只会被上下文截断。建议将 `max_tokens` 设为 1000 至 2000，思维链会占用其中一部分。

另需注意：该模型聊天模板仅接受 `reasoning_effort` 的 `low`、`medium`、`xhigh` 三档，传入 `high` 或 `max` 会返回 400。

# 并行方案

压测中已提及两张卡分担不同层。本节说明并行方式。结论：本次采用 layer 切分，未启用张量并行，数据并行度为 1。

## 开启方式与选择依据

张量并行（**TP**，Tensor Parallelism）切分的是层内权重矩阵。每个 token 的前向过程中，切分后的部分需在卡间交换中间结果并归约，通信发生在每一层甚至每次矩阵乘法之后。其优势在于单层计算可由多卡分担，适用于单层无法放入单卡的场景；代价是通信频繁，对卡间带宽高度敏感。

层间并行以完整层为单位切分。65 层按比例分配至两张卡，前一卡完成若干层后将激活值传递至下一卡，通信仅发生在层边界。优势是通信次数少、实现简单，适合普通 PCIe 环境；限制是每张卡仍持有完整单层，单层显存占用未下降，并行度受层数约束。llama.cpp 默认采用该模式，仅进行层的分配，不包含流水线式重叠调度。

数据并行（**DP**，Data Parallelism）切分的是请求。每张卡或每组卡持有完整模型副本，独立处理不同请求，由前置负载均衡分发。优势是吞吐可随副本数扩展；前提是单卡或单组可容纳完整模型与 KV 缓存。

| 方案     | 开启参数                    | 切分单位与通信                 | 本环境可用性               |
| -------- | --------------------------- | ------------------------------ | -------------------------- |
| 层间并行 | `-sm layer -ts 1,1`（默认） | 完整层与该层 KV，层边界传激活  | 已启用，运行稳定           |
| 张量并行 | `-sm row -ts 1,1`           | 层内权重按行切开，每层跨卡归约 | 可以尝试，但通信开销更大   |
| 单卡     | `-sm none`                  | 不切分                         | 无法容纳完整权重与 256k KV |
| 数据并行 | 无内置参数，多个进程或容器  | 每份副本持完整模型，按请求分流 | 单卡无法容纳完整权重，不可行 |

选择 layer 切分基于三点。第一是通信量：该部署以单请求低延迟为目标，decode 阶段每个 token 都需执行完整前向，通信开销会被持续放大；层间并行仅在层边界传递激活，显著低于层内多次归约。第二是显存粒度：模型 24.03 GB，按 1:1 分层后每卡约 12 GB 权重，剩余空间可容纳视觉投影器与 KV 缓存，且仅需一个比例参数控制。第三是改动成本：模型文件本身按层组织，层切分可按层直接加载，量化格式不受影响。

限制同样明确：每张卡仍持有完整单层，单层显存占用未下降；并行度受 65 层粒度约束；分配不会自动均衡，实测两张卡分别占用 18.9 GB 与 22.1 GB。若目标是降低单层延迟而非扩大可容纳模型，layer 切分无法满足。

当前环境下，张量并行可配置但不推荐。层内归约需经过卡间链路，在没有 NVLink 的 PCIe 环境中，`row` 模式每层均需同步，decode 速度大概率低于当前 layer 模式；量化张量按行切分的实际效果也需重新压测，不能直接假设更快。数据并行不可行：每个副本需一份完整 24.03 GB 权重及独立 KV 缓存，单张 24 GB 卡无法容纳；若以两张卡为一组构成副本，两份副本需四张卡，而另外两张卡已运行其他服务。

# 投机解码

前述仅说明启用方式；本节说明其有效性、代价与未采用另一方案的原因。

## MTP、DFlash 与 DFlash2 的对比

自回归生成每生成一个 token 需执行一次完整前向。单请求场景下 batch size 为 1，GPU 算力利用率低，瓶颈主要为显存带宽。投机解码先由计算成本较低的草稿器预测后续若干 token，再由目标模型一次性并行验证。单次前向成本主要由批大小决定，验证 k 个 token 的增量成本有限；草稿准确时，可将 k 次串行前向压缩为一次。失效条件为草稿命中率不足：错误部分需回退重算，耗时高于逐 token 生成。

因此收益由两个指标决定。**draft acceptance**（草稿接受率）为草稿 token 被目标模型接受的比例；**mean len**（平均命中长度）决定草稿长度参数。经验阈值为接受率 50%，低于该值时验证与回退开销会抵消并行收益。本次实测接受率为 59% 至 77%，平均命中长度 2.18 至 2.54，均高于阈值。

MTP 来自训练阶段：预训练时额外学习“预测下下个 token”的任务，权重中因此包含 nextn 结构；推理时主模型隐状态输入该结构，由其自回归生成草稿。其优势是无需额外模型文件，草稿头位于主模型权重内，不增加独立显存开销，也不存在草稿模型与目标模型不匹配的问题。该模型仅有一层 MTP，草稿链较短，因此每次草拟 2 个 token。

**DFlash**（依赖独立草稿模型的块并行投机方案）属于另一类方案，需要独立草稿模型。其机制为块并行去噪：输入由最后一个真实 token 与若干 mask 占位构成，一次前向将所有 mask 位置填充为候选 token，单步产出整块草稿。块大小默认 16，即最多 15 个草稿 token，单步草稿量比 MTP 高一个数量级。该方案还会从目标模型中间层提取隐藏特征注入草稿，以提高与目标模型的一致性。单步理论收益显著高于 MTP，但需额外下载兼容草稿模型、增加显存占用，且两者必须配套。

**dflash2** 是 DFlash 家族中的另一架构，与 dflash、dspark、lilicorr 并列。基础机制一致：仍需独立草稿模型、采用块并行去噪、使用目标模型中间层特征。差异在于新增 **selector**（候选筛选模块）：块并行去噪会在多个位置同时产生候选，selector 对候选排序挑选，相当于在草稿端执行预筛，优先保留更可能被目标模型接受的候选。其提升的是草稿质量而非数量，实际收益取决于草稿模型与任务的匹配程度，本次未具备实测条件。限制与同族一致：不能与 dflash、dspark、lilicorr 同时启用，也不能与 MTP 共存，因为 MTP 会将其作为草稿源，而该架构同样不含 nextn 层。

| 维度         | MTP                 | DFlash               | DFlash2                  |
| ------------ | ------------------- | -------------------- | ------------------------ |
| 草稿来源     | 主模型内置 nextn 层 | 独立草稿模型         | 独立草稿模型             |
| 额外权重     | 无                  | 有，且占显存         | 有，且占显存             |
| 单步草稿量   | 少，本次实际为 2    | 多，块大小默认 16    | 多，块大小默认 16        |
| 草稿生成方式 | 自回归逐 token      | 块并行去噪           | 块并行去噪 + 候选挑选    |
| 部署复杂度   | 一个启动参数        | 需下载并匹配草稿模型 | 同左，且需匹配该草稿架构 |

两者不能同时启用。参数语法允许以逗号分隔多个类型，但结构上不可行。DFlash 家族内部互斥，dflash、dflash2、dspark、lilicorr 共享同一草稿上下文，仅可启用其一。MTP 与 DFlash 同样不能共存：指定独立草稿模型后，MTP 会将其作为草稿源，而 DFlash 模型不包含 nextn 层，初始化阶段会因结构缺失失败。可与 MTP 同时使用的是 **ngram**（n-gram，按上下文重复片段预测）类投机器，其不依赖草稿模型，适用于代码补全与模板化输出，本次未启用。

本次部署的仓库仅提供主模型的多个量化版本与视觉投影器，不包含任何 DFlash 家族草稿模型（含 dflash2），因此 DFlash 方案不可行，MTP 为唯一可用方案，实测表现符合预期。调优有两条硬性建议：temperature 不超过 1，重复惩罚保持 1，否则草稿分布偏移会显著降低接受率；若特定场景接受率持续低于 50%，说明 MTP 在该场景构成负担，应改用不含 MTP 张量的普通 Q6_K 版本，体积减少约 450 MB。判断 MTP 是否生效不应依据启动参数，而应检查日志中的 `draft acceptance` 行；该行缺失即表示加速未生效。
